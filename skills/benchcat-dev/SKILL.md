# benchcat development

The crate renders one SVG card from canonical benchmark records. Everything below is about changing
it, not using it.

## Layout

```
src/
  lib.rs            module wiring + re-exports
  main.rs           clap CLI: `render`, `formats`
  config.rs         benchcat.toml via config-rs (file + BENCHCAT_* env)
  model/            Benchmark, Meta, Report, Unit, UnitKind, formatting
  input/            format detection + json/jsonl/csv/benchmark_test readers
  adapters/         criterion directory and hyperfine JSON importers
  font/             metrics, outline extraction, file resolution
  layout/           pure geometry: taffy tree, badges, sections, row heights
  svg/              emission: writer, theme, atlas, text, rows, legend, cat badge
  render/           orchestration: series union, bar scaling, placeholders
  rows.rs           [[row]] matching, captures, expressions
  expr.rs           arithmetic used by row `value`
  template.rs       `{placeholder|fallback}` expansion
```

Dependencies only flow downwards: `render` -> `layout` -> `svg` -> `font`/`model`. `layout` must not
know about SVG strings; `svg` must not compute geometry.

## Determinism contract

Two machines must produce byte-identical SVGs:

- no clock, no git calls, no randomness, no `HashMap` iteration order in output;
- directory inputs are sorted before parsing (`input::collect_files`, `adapters::criterion::walk`);
- log compression uses `libm`; every number is formatted by `svg/writer.rs` with a fixed precision,
  and glyph extraction returns results in `gids` order even when rayon runs;
- `.gitattributes` forces LF; never commit a CRLF SVG.

## Map types

The model uses std `BTreeMap` for `params`/`metrics`/`extra`: those maps are tiny, and an A/B run with
the render benchmark showed the bbtree-backed alternative ~20% slower on parse/full because every row
would allocate a 1 KB page on first insert.

Numeric-key `HashMap`s use `hash::BuildIdentity` (see `svg/atlas.rs`, `examples/specimen.rs`); string-key
maps use `hashbrown`. The font caches are `DashMap`, not `Mutex<HashMap>`.

## Parallelism

rayon is used only where work is independent and the original order can be restored:

- long JSONL / benchmark_test files (>= 2000 lines) parse line blocks in parallel, then flatten in
  block order; line numbers in errors are preserved;
- several input files (>= 2 files, >= 128 KiB) parse in parallel; the merge keeps argv order;
- glyph outlines use `extract_paths` above 96 unique glyphs;
- rows of a card (>= 256 rows) are emitted in four fixed chunks: each chunk builds its own buffer and
  the buffers are concatenated in order, so the bytes are identical to the sequential pass. Four is
  the CI runner core count; more chunks regress on large machines. Chunk buffers add roughly one SVG
  of peak memory, so very large cards trade memory for time.

The font caches are `DashMap` with the identity hasher, so parallel readers only contend per shard.
Before that change a parallel emission prototype was slower above two threads; do not go back to a
global `RwLock` around those caches.

cargo fmt --all -- --check

cargo run --example gallery -- --only 14 --png # one asset while iterating
cargo run --example specimen -- --font quicksand

`gallery` and `specimen` accept `--only`/`--font` (prefix match) and `--list`. Only run the full
regeneration for a final verification; commit code and regenerated bytes together.

## Benchmark

`benches/render.rs` is a development-only benchmark; nothing in CI runs it. The verify job tests
explicit targets (`--lib --bins --tests --examples`), not `--all-targets` (which would execute the bench
target), and no workflow calls `cargo bench`.

```bash
cargo bench --bench render
cargo bench --bench render -- --rows 20000 --series 3 --iterations 20
cargo bench --bench render -- --rows 1000,5000 --phases parse,render --json
```

The corpus is generated in a temporary directory as canonical JSONL, so timings include real file I/O
and the same parser the CLI uses.

| phase | measures |
| --- | --- |
| `font` | cold `load_font` (path lookup + parse) |
| `parse` | `input::load` over every source file |
| `render` | layout + SVG emission from already-parsed rows |
| `full` | parse + render (the CLI work, minus startup and font loading) |

Parameters: `--rows`, `--series`, `--iterations`, `--warmup`, `--font`, `--font-file`, `--group-size`,
`--note-every`, `--bar-scale`, `--bar-curve`, `--missing`, `--max-rows`, `--phases`, `--json`, `--keep`.
Results report median/min/p95, rows per second and SVG bytes; `--keep` leaves the corpus behind for
profiling with `perf` / `samply`.

## Layout engine

`layout/engine.rs` uses taffy only for the vertical flow: header, one sized leaf per section, footer.
Row geometry is computed directly, because a node per grid cell cost ~1.8 µs each and dominated the
profile.

- A section leaf gets `TextSpec::fixed(width, height)`: taffy calls the measure closure for every leaf,
  and a context-less leaf measures as zero, so the fixed spec is what carries the block size.
- Tracks (label, bar, value, RME) are whole pixels, rounded by cumulative boundary
  (`round(b1)`, `round(b1 + b2)`, ...) so a row keeps the width the old grid produced.
- Row height in a comparison card:
  - 0 or 1 drawn bar: exactly `card_height` (the single-source height), never the fullest row's height;
  - 2+ bars: `max(card_height, bar_height * count + gaps + 20, label block + 18, badge + 12)`,
    rounded to a whole pixel.
- Bar thickness follows the card, not the row: 6 px in a comparison card (even a lone bar), 10 px in a
  single-source card.
- Per-row x: label at `card.x + number_gutter`, bar at `card.x + label_w + 12`, value and RME after the
  bar; bars stack vertically centred in the card.
- `min_height` is applied after the layout pass by pushing the footer down and setting `plan.height`.
- Columns: label/bar/value widths are clamped to fractions of the content width; keep the clamp bounds
  ordered (`.max(min)`) so narrow widths cannot panic.
- Badges: `layout/badge.rs` computes a cat whose body stretches with the digit count; digits are
  ink-centred, not box-centred.

## SVG writer

All emission goes through `svg/writer.rs`; do not build markup with `format!` or `push_str` on ad-hoc
strings.

- `open/close/empty`, `attr/attr_raw/attr_num/attr_id/attr_fmt`, `text/raw/end`, `finish`.
- `attr` escapes `& < > " '`; `attr_raw` is only for values this crate generated (colours, path data).
- `attr_num` prints whole numbers without the format machinery but with the same digits as `{:.N}`;
  changing a precision changes committed assets.
- The writer owns one pre-sized buffer: header, defs, decorations and rows all append to it. Do not
  reintroduce a second body buffer.
- Glyph ids resolve through `Atlas::index` (`gid -> path id`, `u32::MAX` = absent), not a HashMap.

## Render pipeline

`render/mod.rs` -> `merge.rs`:

1. Build the id union in first-seen order and one slot per series.
2. Choose a reference per row/source/global (`bar_scale`) and a curve (`bar_curve`); single-source
   cards always use the global best with the log curve.
3. Missing slots become `present: false` (`missing = "skip"`) or an empty bar with an em dash.
4. `missing = "skip"` sets `present: false`; `"placeholder"` draws an empty track and an em dash.
5. Build `RowPlan`s, then `layout::layout`, then `svg::render`.

## Allocator

The binary uses `mimalloc` as its global allocator (`src/main.rs`). It is a target-specific dependency,
so the musl releases keep the system allocator and do not need a C toolchain for that target.

Allocation was a real bottleneck: switching allocators cut a 20k-row card from 420 ms to 299 ms at one
thread and from 315 ms to 242 ms at 32 threads. Peak RSS goes up because mimalloc keeps freed pages
(20k rows / 36 MB SVG: 158 MB -> 315 MB); that is the trade-off to revisit if very large cards become
memory-bound.

## Fonts

`font/` keeps `skrifa` only for parsing; no font is embedded.

- `metrics.rs`: advances, ink boxes, line heights.
- `outline.rs`: `path` cache, `glyph_bounds`, rayon `extract_paths` above 96 glyphs.
- `resolve.rs`: explicit file -> `./fonts/<family>.ttf` (default family `mplus-rounded`) -> first
  TTF/OTF on disk -> `BENCHCAT_FONT_DIR` entries.

Caches and lookups:

- `glyphs` is a `hashbrown` map keyed by `char` with the identity hasher (`crate::hash::BuildIdentity`);
  codepoints are already unique, so they are not hashed again.
- `paths` / `bounds` are `DashMap<u16, _, BuildIdentity>`: only the glyphs that are actually used cost
  memory, and concurrent readers do not serialise. Never turn these into `Vec` indexed by gid — gids are
  sparse and a face can address up to `u16::MAX`, so a dense vector would waste memory.
- String-key maps (`dedupe`, `merge`) use `hashbrown` with its default foldhash.
- No map is iterated to produce output order: `dedupe` and `merge` walk `Vec`s, and map iteration only
  folds max/min.

The gallery defaults to `mplus-rounded`; changing the default font changes every committed asset.

## Config

`Config::load` layers the TOML file with `BENCHCAT_*` environment overrides through `config-rs`
(`toml` feature only). Add new keys to `Render` with a serde default, update `Default`, document them in
the README and the integration skill, and add a gallery example if the key changes output.

## Gallery and specimens

- `examples/gallery.rs` holds one block per figure (`01-basic` ... `15-bar-scale`).
- `examples/specimen.rs` renders one type specimen per TTF/OTF in `fonts/`.
- New behaviour must land as a new gallery example, generated with the real code path.
- Assets live under `assets/examples/` and `assets/fonts/`; the CI `assets` job regenerates and commits
  them on Linux. Never hand-edit or hand-merge an SVG.

## Release

`.github/workflows/bundle.yml` is one ordered workflow: verify (3 OS) -> byte identity -> assets -> action
test (3 OS) -> build 6 targets -> publish. Tags are `v$(date -u +%Y.%m.%d)-${GITHUB_SHA::7}`; the GitHub
Action installs the binary from the release itself. Marketplace needs a SemVer tag, which date tags are
not.

After a successful release, a `consumer` job runs the action by reference
(`unk-404/benchcat@master`, not `uses: ./`) on Ubuntu and Windows and installs the freshly
published binary. This is the
only job that exercises the composite-action download path: GitHub leaves `GITHUB_ACTION_REPOSITORY`
empty inside composite steps ([community #49245](https://github.com/orgs/community/discussions/49245)),
so `install.sh` derives `owner/repo` from `GITHUB_ACTION_PATH` (`…/_actions/<owner>/<repo>/<ref>`) and
falls back to `GITHUB_REPOSITORY` for a local `uses: ./`.

A `changes` job classifies the pushed range (or the PR merge base) and sizes the run:

| changed paths | runs |
|---|---|
| `Cargo.toml`, `Cargo.lock`, `src/`, `examples/`, `.cargo/`, `rust-toolchain*`, `.gitattributes` | full chain, and outside PRs a release build + publish |
| `fonts/`, `assets/` | assets only (fonts are runtime inputs, not compiled in) |
| `scripts/`, `action.yml`, `templates/`, `.github/` | the action test only |
| markdown, `LICENSE`, `.gitignore` | nothing beyond classification |
| anything unrecognised | full chain (safe default) |

Mixed changes run the union; a binary change always implies assets and the action test. `pull_request`
and `workflow_dispatch` runs are classified the same way, and the workflow pins Rust 1.99.0 through the
`toolchain:` inputs, so local builds should use the same version (`rustup run 1.99.0 cargo ...`) when
comparing bytes. Every cargo invocation uses `--locked`, so a manifest change without an updated lock
fails instead of silently resolving a new graph. The action job also runs `scripts/install.sh` against
the latest release, so installer changes are tested without a rebuild.

## Where to change what

| Want | Touch |
|---|---|
| new card element / colour | `svg/theme.rs`, `svg/emit.rs` |
| new geometry rule | `layout/engine.rs` |
| new input format | `input/` or `adapters/`, then `Format` |
| new config key | `config.rs`, `render/`, docs |
| bar scaling policy | `render/merge.rs` (`bar_scale`, `bar_curve`) |
| font metrics | `font/metrics.rs` |
| placeholders / captures | `template.rs`, `rows.rs` |
